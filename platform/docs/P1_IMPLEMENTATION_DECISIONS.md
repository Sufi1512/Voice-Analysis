# P1 implementation decisions

Choices made while building P1 tickets that the spec leaves open. Same format as
`P0_IMPLEMENTATION_DECISIONS.md`. Each is covered by the ticket's tests.

| # | Ticket | Decision | Reason |
|---|---|---|---|
| D1 | C2 | Global tables (users, sessions, reset tokens, login throttle) have no row-level security and are read by `nexora_app`; `nexora_admin` (BYPASSRLS) is kept for tenant-table lookups before an organization is known (invitation tokens) and platform-owner actions. | The bypass role is never used where the app role suffices. |
| D2 | C4 | Audit writes for one organization are serialised with `pg_advisory_xact_lock(hashtext('audit:' \|\| org))`; the service sets `occurred_at` and it is inside the hash. | The app role cannot lock or change audit rows, so row locks are not available; a database default timestamp would not be known before hashing. |
| D3 | C4 | `record()` refuses details keys containing password, token, secret, code or otp. | Audit rows are permanent; secrets must never land there. |
| D4 | C5 | Cookies use the `__Host-` prefix (`__Host-nexora_session`, HttpOnly; `__Host-nexora_csrf`, readable by the portal). | Browsers then require Secure, Path=/ and no Domain, so a sibling subdomain cannot set or shadow them. |
| D5 | C5 | Double-submit CSRF applies to every unsafe `/v1/` request, login included; `GET /v1/auth/csrf` issues the token, and login rotates it. | Covers login CSRF without a separate mechanism. |
| D6 | C5 | Lockout counts failures for unknown emails too, and an unknown email spends one argon2 verification against a dummy hash. | Same response and timing for "no such user" and "wrong password", so emails cannot be enumerated. |
| D7 | C5 | A per-IP limit (100 failures a minute, 15-minute lock) runs alongside the per-email limit (10). **Deploy must set uvicorn `--forwarded-allow-ips` to the reverse proxy**, or every user shares the proxy's address. | Spec asks for per-IP and per-email limits; the IP limit is set high so an office NAT is not locked out. |
| D8 | C5 | Signing in revokes the session in the incoming cookie. | No session fixation and no stale sessions left behind. |
| D9 | C5 | Request time comes from `app.state.clock` (UTC), never from database `now()`, for session and throttle checks. | Tests move time precisely; one source of time per request. |
| D10 | C6 | The catalogue holds only permissions P1 endpoints check; each later phase adds its own in code and a migration. Migration 0003 stores a literal snapshot, and a test fails if code and database differ. | No guessed permissions for features that don't exist yet; migrations never change meaning when code moves on. |
| D11 | C6 | A workspace-only membership grants `organization:read` at organization level; its role's permissions apply inside that workspace once workspace endpoints exist (C9). An organization-wide membership grants its role everywhere in the organization. | Invites default to Viewer at organization scope (AC-4d), so roles are not tied to one scope. |
| D12 | C6 | The platform owner passes every check in any existing organization (DB doc §3.2 check order). A missing organization is 404 for everyone. | Follows the approved architecture; revisit if customer contracts forbid operator access to tenant data. |
| D13 | C6 | `GET /v1/organizations` uses a SECURITY DEFINER function returning only id, name, slug and role for one user's memberships, instead of a BYPASSRLS connection. | Narrowest way to read across tenants for this one list. |
| D14 | C6 | The app mounts routers from one list (`ROUTERS`), and the endpoint-by-role matrix is generated from that list; a guard test fails if any `{org}` route lacks `require(permission)`. | FastAPI 0.162 keeps included routers as private `_IncludedRouter` objects; the list is public and complete by construction. |
| D15 | C7 | The first platform owner is created **without a password**; a single-use 24-hour set-password token (SHA-256 in `password_resets`) is written to `NEXORA_BOOTSTRAP_TOKEN_FILE` (mode 0600, new directory 0700) and consumed by the reset flow (C10). An expired, unused token is reissued on the next start; an advisory lock makes parallel starts safe. | The ticket said "one-time password file"; a reusable password on disk would stay valid after the file leaked. A token works once and expires. |
| D16 | C7 | If a user with the bootstrap email already exists, they are promoted (a warning is logged); once any platform owner exists, the setting is ignored. | Deploy-time configuration is trusted; a second owner never appears from a changed variable. |
| D17 | C7 | `POST /v1/platform/organizations` returns the invitation's id, email, role and expiry, never its token; non-owners get 403 naming `platform:organizations`. The list uses a SECURITY DEFINER function (as D13). | The token only travels by email (C8). |
| D18 | C8 | The invitation email is sent inside the request's transaction; if SMTP fails the request returns 502 `email_failed` and the invitation is rolled back. | Never an invitation nobody received. (If the commit failed after sending, the emailed link would simply not work.) |
| D19 | C8 | Invitation links put the token in the URL fragment (`/invite#<token>`). | Browsers never send fragments to servers or in Referer headers, so tokens stay out of access logs. |
| D20 | C8 | Inviters can't grant a role ranked above their own; Organization owner/admin can only be organization-wide; inviters without `member:manage` (workspace admins) must name a workspace in their own organization. Re-inviting the same person and scope revokes the pending invitation. | Least privilege; no stale links. |
| D21 | C8 | Accepting claims the invitation first (row-locking UPDATE), then creates or confirms the user; any later refusal rolls the claim back. A new user sets a 12+ character password; an existing user confirms with their password (counted by the login lockout) or by being signed in as that account; signed in as anyone else is refused. Accepting verifies the email and signs the user in. | A race test found that creating the user before claiming let two simultaneous acceptances collide (500); claiming first makes the loser get 410. |
| D22 | C8 | Invitation lookup by token uses a SECURITY DEFINER function (exact SHA-256 match), not the BYPASSRLS role. | As D13. |
| D23 | C8 | Unit tests use an in-process SMTP server (aiosmtpd, real protocol); CI also runs Mailpit (`axllent/mailpit:v1.20.0`) with a delivery test. Docker Hub is not reachable from the development workspace. | "Mailpit in tests" where Mailpit can run; the SMTP code path is tested everywhere. |
| D24 | C8 | Production refuses `smtp_security = none` (STARTTLS or TLS required); header values from data (organization names) are stripped of CR/LF. | No plaintext credentials or mail in production; no header injection. |

Known limit: anyone who knows an email can lock it for 15 minutes by failing 10 sign-ins. This is
inherent to the lockout the spec requires (AC-3); the generic error keeps it from revealing whether the
account exists.
